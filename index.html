Khelaw

Find a free slot. Book it in under a minute.

Khelaw is an indoor sports venue — turf, futsal, cricket, badminton — booking and management platform built for Bangladesh. Players see what's free near them right now and book it before anyone else does. Owners get every slot, payment and customer on one screen instead of a notebook and a ringing phone. খেলোয়াড়রা কাছাকাছি খালি স্লট দেখে এক মিনিটে বুক করতে পারবে, আর ভেন্যু মালিকরা সব বুকিং, পেমেন্ট ও কাস্টমার এক জায়গায় দেখতে পারবেন।

The problem & the answer

From a notebook and a ringing phone, to one screen.

Privately owned turf venues in Bangladesh rent by the hour — and today the whole business runs on memory, WhatsApp and luck. Khelaw replaces that with a two-sided platform: a booking engine players can trust, and an operations console owners actually want to open. বাংলাদেশের ইনডোর টার্ফ ভেন্যুগুলোর জন্য একটি সম্পূর্ণ ডিজিটাল বুকিং ও ম্যানেজমেন্ট প্ল্যাটফর্ম।

Today

The old way

  • ✕Bookings tracked in a notebook, WhatsApp or memory — double bookings and forgotten slots are routine.
  • ✕Owners spend the day answering calls asking “is 9–10 PM free tomorrow?”.
  • ✕bKash / Nagad advances verified by hand, with no link between a payment and a booking.
  • ✕No data: which hours are dead, who the regulars are, what was earned this month.
  • ✕Players call several venues one by one, get no answer, and arrive to find the slot taken.
With Khelaw

The new way

  • ✓Real-time slot availability, held for 10 minutes while the player pays — no double bookings, by database constraint.
  • ✓Every request, payment and customer on one owner dashboard, with push + email the moment something changes.
  • ✓Manual bKash / Nagad / Rocket / Upay transfer with a generated reference — verified by a human, on both sides.
  • ✓Revenue, occupancy, peak-hour heatmaps and customer history — the data the notebook never had.
  • ✓One search, one map, one tap — see what's free near you and book it before someone else does.

The heart of the product

A booking in five steps.

Nothing about a slot is decided by the client. The server generates it, prices it, holds it, and PostgreSQL guarantees it can only be sold once.

1
Pick a slot

Availability is generated from the venue's operating hours, closures, booking window and existing bookings.

2
Hold it

The server creates a 10-minute hold and returns the price breakdown, the advance amount and a payment reference.

3
Pay & submit proof

The player transfers to the venue's wallet using the reference, then submits sender number, transaction ID and screenshot.

4
Venue confirms

The owner checks the proof and confirms. The player is notified on every channel and gets a QR ticket.

5
Play & check in

The venue scans the QR at the gate. The booking auto-completes at the end time, and a review prompt follows.

Two rules before touching the code

Correctness is not a feature. It is the foundation.

These two rules are the reason the booking engine can be trusted. Everything else in the platform is built on top of them.

RULE 01

Double booking is prevented by PostgreSQL

Not by an application check. A GiST exclusion constraint on (court_id, time_range) covers holds, pending, confirmed and checked-in bookings — plus offline bookings and owner blocks, which live in the same table.

-- never replace with an application-level check ALTER TABLE booking ADD CONSTRAINT booking_no_overlap EXCLUDE USING gist (court_id WITH =, time_range WITH &&) WHERE (status IN ('HOLD','PENDING','CONFIRMED','CHECKED_IN'));
RULE 02

A slot belongs to the operating day it started on

A venue open Tuesday 15:00 → Wednesday 02:00 has its 01:00 slot on Tuesday. Every date filter, search query and availability response uses this — not the calendar date.

// venue open Tue 15:00 → Wed 02:00 01:00–02:00 on Wednesday → operatingDate = Tuesday // search "Tue 23:00–01:00" must match it
How it makes money

A per-venue subscription, not a cut of the game.

Khelaw never holds player money. Booking advances go straight to the owner's own wallet. The platform's revenue is a subscription the venue pays to stay listed.

How listing visibility works

A venue is visible to players only while all three are true:

  • the venue is ACTIVE,
  • its setup checklist is complete, and
  • a subscription period is active now (trial, paid or grace).

When it lapses, the venue disappears from home, search, map and booking — but confirmed bookings stay valid and owner mode keeps working, with a red banner to renew. No payment gateway, no escrow: every transfer is manual, with a generated reference, verified by a human.

Not code — humans

What's left before a public launch.

The application runs locally, but production needs accounts and credentials that only a person can create.

Deployment

The backend has not been deployed yet. The first production deploy is a milestone in its own right — after it, API breaking changes require a new version.

Domain authentication

SPF, DKIM and DMARC records for khelaw.site must be set up in Brevo, or transactional email will land in spam.

Credentials & keys

Cloudflare R2 buckets, the Brevo API key, the Firebase service account and google-services.json, and a Google Maps API key for Android.
